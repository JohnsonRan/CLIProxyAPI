# Downstream Fork Maintenance Guide (`JohnsonRan/CLIProxyAPI`)

This repository is a maintained downstream distribution of [`router-for-me/CLIProxyAPI`](https://github.com/router-for-me/CLIProxyAPI). It tracks `upstream/main` and layers independently reviewable, buildable, and testable patches on top of the latest upstream baseline.

## Branch Architecture

- **Upstream baseline**: `https://github.com/router-for-me/CLIProxyAPI.git` (`main`)
- **`ci`**: Downstream maintenance overlay carrying this `MAINTAIN.md`, downstream `README.md` notice, `.github/workflows/upstream-sync.yml`, `.github/workflows/ghcr-docker.yml`, the combination-conflict resolver `.github/scripts/resolve-union-conflict.sh`, and multi-patch integration tests (`sdk/api/handlers/downstream_client_access_combination_test.go`, `internal/api/downstream_commandcode_systemone_combination_test.go`; they compile only on the integrated tree). Never mix product runtime changes into `ci`.
- **`patch/<name>`**: Independent product patch branches, each branched directly from `upstream/main` and kept suitable for standalone review and independent build/test. One patch carries one feature or fix, so a patch becomes empty once upstream absorbs it.
- **`main`**: Integrated release branch rebuilt from `upstream/main` with one countable squash commit per branch (`merge ci branch` followed by each `merge patch/<name> branch` in fixed order). Never commit fixes only to `main`.

The integration order lives in `PATCH_BRANCHES` in `.github/workflows/upstream-sync.yml`. Keep it identical to the list below.

## Active Patch Branches (Fixed Integration Order)

1. **`patch/http-compression`**
   - **Goal**: End-to-end HTTP, SSE, and WebSocket compression (`gzip`, `br`, `zstd`, `deflate`) across both downstream and upstream legs.
   - **Scope**:
     - Downstream request body decompression (`sdk/api/handlers/request_body.go`, `internal/api/middleware/request_logging.go`, and the Claude, Gemini and `/v1/alpha/search` handlers) supporting `gzip`, `br`, `zstd`, `deflate`, multi-coding chains, and magic-byte `gzip`/`zstd` detection. Decoded size is capped by `max-request-body-bytes`, or by default at 256 MiB in handlers and 32 MiB in the pre-auth request log copy; zstd request windows are capped at 8 MiB; `/v1/alpha/search` keeps its 16 MiB ceiling.
     - Downstream HTTP & SSE response compression middleware (`internal/api/middleware/response_compression.go`) negotiating `zstd > br > gzip > deflate`, flushing stream encoders on every SSE flush, with small per-stream encoders (zstd 1 MiB window, brotli quality 5 / 256 KiB window), skipping image/video/audio/archive bodies and 206 responses and weakening strong `ETag`s, plus `EnableCompression: true` on `wsrelay` and `codex/live` WebSocket upgraders/dialers.
     - Upstream HTTP response decompression (`internal/runtime/executor/helps/response_compression.go`) across `codex`, `openai-compatibility`, `gemini`, `antigravity`, `kimi`, `xai`, and `meta` executors. zstd bodies are decoded synchronously (`WithDecoderConcurrency(1)`, about 2x faster and a third of the allocations of the default four-worker decoder on SSE streams) with the window capped at 64 MiB.
     - Upstream request body compression (`upstream.codex.upstream-request-compression`) defaulting to `zstd` level 3 for `chatgpt.com` `/responses` and `/responses/compact` bodies of at least 1024 bytes.
   - **Related Upstream Work**: PR [#5132](https://github.com/router-for-me/CLIProxyAPI/pull/5132), PR [#4461](https://github.com/router-for-me/CLIProxyAPI/pull/4461).

2. **`patch/responses-ws-sse-incremental`**
   - **Goal**: HTTP incremental SSE, standard/incremental WebSocket normalization, and the HTTP-to-WebSocket upstream bridge.
   - **Scope**:
     - `permessage-deflate` on the `/v1/responses` WebSocket upgrader.
     - WebSocket request normalization: default omitted `"type"` to `"response.create"`, coerce string `"input"`, inherit `tools`, `tool_choice`, and `parallel_tool_calls` across incremental turns, and keep prewarm `additional_tools`.
     - HTTP continuation (`openai_responses_http_incremental.go`): `POST /v1/responses` with `previous_response_id` plus delta `input` expands the cached history for stateless upstreams. No executor forwards `previous_response_id`, so an unknown, expired or foreign id, or a delta that cannot be merged, returns `400 previous_response_not_found` instead of sending the delta without its history; the client then resends the full input. WebSocket turns merged locally (HTTP upstream mode) are written to the same cache, so a new socket can continue a `previous_response_id` from an earlier socket or an HTTP turn, and HTTP can continue a WebSocket turn; native WebSocket upstream passthrough is unchanged. Entries are bound to the creating caller (access provider and client key), expire after 30 minutes, and are capped at 1024 entries and 256 MiB. Every turn's canonical request repeats the whole history, so the cache (`openai_responses_http_state_cache.go`) interns input and output array elements and the request without its input by content (maphash, verified byte for byte, private on collision) and reference-counts them: a conversation costs O(turns) bytes instead of O(turns²), and the byte cap counts each shared chunk once. Compact arrays, which the merge path writes, round-trip byte for byte. 40-turn conversation with 2 KiB items: 3.66 MB → 0.20 MB retained; the cache was 241 MB of a 290 MB live heap in the 2026-10-18 profile.
     - HTTP-to-WebSocket bridge: the global `oauth.providers.codex.enable-websocket-upstream` switch, or a per-credential `websockets: true`, routes HTTP/SSE clients through the Codex WebSocket upstream while `/responses/compact` and `/v1/images/*` stay on HTTP. **Downstream semantics**: upstream's per-credential `websockets` only affects WebSocket clients; here it also bridges HTTP clients and overrides the global switch. The panel patch `patch/websocket-upstream-toggle` exposes the global switch and documents this.
   - **Related Upstream Work**: PR [#6705](https://github.com/router-for-me/CLIProxyAPI/pull/6705) (independent HTTP continuation implementation; WebSocket continuation stays connection-scoped there), PR [#4907](https://github.com/router-for-me/CLIProxyAPI/pull/4907), PR [#3562](https://github.com/router-for-me/CLIProxyAPI/pull/3562), PR [#5420](https://github.com/router-for-me/CLIProxyAPI/pull/5420), Issue [#2596](https://github.com/router-for-me/CLIProxyAPI/issues/2596).

16. **`patch/proxy-transport-reuse`**
    - **Goal**: Reuse proxied upstream connections and make SOCKS5 dials cancellable.
    - **Scope**:
      - `cachedProxyTransport` (`internal/runtime/executor/helps/proxy_helpers.go`) keeps one `http.Transport` per proxy URL in a bounded LRU for `NewProxyAwareHTTPClient` and the non-Anthropic/non-ChatGPT fallback of `NewUtlsHTTPClient`. Before, every request with a request, credential, or global proxy URL built a new transport: a fresh TCP, proxy, and TLS handshake per call, with the discarded idle sockets left open for 90 seconds. 18. **`patch/model-capabilities`**
    - **Goal**: Let clients classify models and read their limits and reasoning support from the plain model list alone, without guessed values.
    - **Scope**:
      - `/v1/models` entries carry OpenRouter-style `architecture.input_modalities`, `architecture.output_modalities`, `architecture.modality` and `context_length` from the registry (`internal/registry/model_architecture.go`). Unknown modalities are omitted, never guessed.
      - Output modalities use OpenRouter names: `text`, `image`, `embeddings`, `rerank`, `decisions`. Built-in models take them from `models.json`; configured `image: true` models default to `[image]`; patches 14 and 17 map `embedding`, `rerank` and `systemone`. Explicit `output-modalities` always wins. Keep config flags named after endpoints (`systemone`, not `decisions`); only the listing uses the modality vocabulary.
      - The Codex client catalog (`/v1/models?client_version=...`) marks models whose outputs are only `embeddings`, `rerank` or `decisions` with `visibility: hide`, like image and speech models.
      - Plain `/v1/models` also carries, when declared: `name` (display name) and `top_provider.max_completion_tokens` (OpenRouter format). `context_length` and the output limit fall back to `inputTokenLimit`/`outputTokenLimit` for Gemini-style catalogs; the configured `max-context-length` override is folded into `context_length` and keeps priority. The registry exposes the limits as separate `input_token_limit`/`output_token_limit` map keys so the Codex catalog, which reads `context_length`/`max_completion_tokens`, is unchanged.
      - `reasoning` is tri-state (`internal/registry/model_reasoning.go`): absent = unknown; `{"supported": false}` = the proxy strips reasoning (registered non-user-defined model without `Thinking`, or explicitly empty thinking config); otherwise `{"supported": true, "levels": [...], "budget": {min, max, zero_allowed, dynamic_allowed}}` with levels as wire values and each part only when declared. User-defined models without explicit thinking stay unknown, and the low/medium/high fallback applied to openai-compatibility models without a thinking config is marked `ModelInfo.DefaultThinking` and never advertised. User-defined models matched to the static catalog report catalog levels that the proxy passes through unvalidated.
      - All additions are additive; unknown values are omitted rather than guessed.
    - **Cross-repo**: `JohnsonRan/pi-cliproxyapi-provider` registers models by `architecture.output_modalities` (decisions as Pi classifiers). `JohnsonRan/dsh-cliproxyapi-provider` (DeepSeek Harness) reads the plain list instead of the Codex catalog, whose template fallback guesses modalities, reasoning levels and context windows for uncatalogued models.

Results are cached per credential for `cache-ttl-seconds` (default 300, minimum 30, failures included), concurrent probes of a credential are collapsed with singleflight, at most 4 provider probes run at once across all requests, and the cache is pruned against the whole pool. `quota-api.enabled` is ignored but still accepted so older configs validate. The selection lives under `quota-api` rather than on `access.api-keys` entries because `patch/client-api-key-models` rewrites those entries on save (core `foldClientKeysIntoAPIKeys`, panel `serializeClientApiKeyItem`) and would drop an unknown field; there is no dependency on that patch. The raw-bodies-only contract (version 1) was replaced on 2026-10-18; an earlier Sub2API-compatible envelope for CC Switch and Minis was dropped on 2026-10-16.

A renamed or deleted auth file, or an edited API key or base URL (which changes the auth index), leaves a stale selection that matches nothing until it is cleared. Relays work only when the upstream proxy runs this patch with the version 2 contract and selected its accounts for the key; a proxy running an older build of this patch does not forward `X-CLIProxy-Usage-Via`, so a loop through it ends at the depth limit (`relay depth limit reached`) instead; any other upstream reports `upstream quota endpoint returned 404` or `upstream does not report quota`. A selected API key whose base URL is an official provider endpoint is probed as a relay and reports an error. Paid xAI accounts without billing data report an error (the panel's chat ping is not replicated). Kimi, Meta, Devin and plugin quotas are not covered. Each probe, relays included, is bounded by a 20 s timeout (listed in `AGENTS.md`).
    - **Cross-repo**: The panel patch `patch/quota-api` (stacked on panel `patch/client-key-provider-scope`) picks each key's credentials in the API keys dialog, including provider keys with a custom base URL as relays (stored by auth index, which needs panel `patch/config-auth-index`; a relay using one of this proxy's own client keys is flagged as a likely loop), and edits the cache TTL; panel `patch/upstream-quota` shows the summary an upstream proxy shares with a provider key.     - **Retire when**: Upstream exposes credential quota to client keys.

34. **`patch/responses-ws-terminal-error-race`**
    - **Goal**: Deliver an upstream error to Responses WebSocket clients instead of an abnormal closure.
    - **Scope**: On a failing upstream request the stream producer (`sdk/api/handlers/handlers_stream.go`) buffers its terminal error and then closes the error and data channels. When `forwardResponsesWebsocket` was not already waiting in `select`, both cases were ready and `select` picked one at random; picking the closed data channel reported `stream closed before response.completed` (408) and closed the socket without a close frame, so the client saw 1006 instead of the error event of a request fault or the 1012 `upstream requires HTTP replay` close of a pinned credential failure (`openai_responses_websocket_forward.go`). The forwarder now lets the next iteration deliver a buffered error when the data channel closes, as every HTTP forwarder already does with `handlers.PendingStreamError`; an unbuffered error channel has length zero and keeps the previous behavior. Upstream errors that are deliberately not exposed (credential and server faults outside the pinned-replay path) still end in a plain close, as before. `TestForwardResponsesWebsocketPrefersBufferedTerminalError` makes both channels ready 64 times and fails on the previous code at the first or second iteration. This was the intermittent failure of `TestResponsesWebsocketReplaysImmediatelyAfterPinnedAuthFailure` (measured on 2026-10-18: 4 of 300 runs at `-cpu 2` on Windows, 1 of 3000 in WSL), so the validation step now runs `-race` over the whole `sdk/api/handlers/openai` package.
    - **Related Upstream Work**: None found (searched `stream closed before response.completed`, websocket 1006, abnormal closure, `forwardResponsesWebsocket` on 2026-10-18). Issue [#4787](https://github.com/router-for-me/CLIProxyAPI/issues/4787) and [#4819](https://github.com/router-for-me/CLIProxyAPI/issues/4819) concern 1006 from the Codex upstream, not this downstream race.
    - **Retire when**: Upstream checks for a pending stream error when the WebSocket data channel closes.

35. **`patch/antigravity-tool-schema-single-pass`**
    - **Goal**: Stop rewriting the whole Antigravity tools document once per function declaration.
    - **Scope**: `sanitizeAntigravityToolSchemaDocumentForModel` (`internal/runtime/executor/antigravity_executor_request.go`) renamed `parametersJsonSchema` with `util.RenameKey` (one set and one delete) and wrote every cleaned schema back with `sjson`, each a full copy of the tools document, so cost grew with declarations x tools size. `sanitizeAntigravityToolsArrayForModel` now renames and cleans each declaration on its own and splices the changed declarations into the tools array in one pass; the per-path rewrite stays as the fallback when a declaration offset cannot be confirmed; the tests compare against a frozen copy of the pre-change rewrite (`legacyAntigravityToolSchemasPerPath`), not against that fallback. Output is byte-identical (`TestSanitizeAntigravityToolSchemasSinglePassMatchesPerPathRewrite`) except for a tool object with two `functionDeclarations` keys, where gjson and sjson resolved the path to different keys and the old rewrite mixed the declarations (`TestSanitizeAntigravityToolSchemasDuplicateDeclarationKey`). `TestSanitizeAntigravityToolSchemasScalesLinearly` fails on the old code (4x declarations: 15x the bytes). 500 small declarations: 295 ms -> 9.7 ms, 284 MB -> 11.7 MB per call. The path was 9% of CPU and 2.2 GB of 16 GB allocated in the 2026-10-18 13:17 profile.
    - **Related Upstream Work**: Issue [#6714](https://github.com/router-for-me/CLIProxyAPI/issues/6714) (open, no PR; same diagnosis and approach). Issue [#6713](https://github.com/router-for-me/CLIProxyAPI/issues/6713) (open; the schema cleaner itself is quadratic in schema size) is not addressed: about 3% of CPU in the same profile, and a rewrite of its twenty phases, shared with Gemini, carries more regression risk than it saves.
    - **Retire when**: Upstream fixes #6714.

36. **`patch/antigravity-replay-signature-guard`**
    - **Goal**: Stop deleting absent thought signatures from every history part when fingerprinting the Antigravity replay context.
    - **Scope**: `antigravityReplayContextFingerprints.at` (`internal/runtime/executor/antigravity_reasoning_replay.go`) ran three `sjson.DeleteBytes` per part before canonicalizing it (0.22 s of the 1.12 s fingerprint path in the 2026-10-18 13:17 profile). Context fingerprints are stored in replay items shared through Home, so instances built with different Go versions must hash identical bytes; a hand-written replica of `json.Marshal` is a cross-instance contract that the gain (a few percent of an idle process) does not justify.
    - **Related Upstream Work**: None found (searched reasoning replay, context fingerprint, replay performance on 2026-10-18).

37. **`patch/responses-ws-interrupt-window`**
    - **Goal**: Reject a `response.interrupt` that arrives after a Responses WebSocket turn has ended, instead of answering it as if the turn were still running.
    - **Scope**: `forwardResponsesWebsocket` (`sdk/api/handlers/openai/openai_responses_websocket_forward.go`) opened the local interrupt window when it started and closed it only when the upstream data channel closed, which can be after `response.completed` reached the client. An interrupt sent in that gap, which the executor reports as `ErrNoActiveUpstreamWebsocket`, was delivered locally: the client got a synthetic `response.incomplete` carrying its `response_id`, or no reply at all when the forwarder returned and `end()` drained the frame. The window now closes on `response.completed`, `response.done`, `response.incomplete` and `response.failed` before the event is written downstream, and reopens on the next `response.created`. This is the race behind the `TestResponsesLateInterruptDoesNotPoisonNextCreate` failures at `openai_responses_late_interrupt_test.go:147` (both the `i/o timeout` and the `response.incomplete` for `unknown`), which failed three `Upstream Sync` attempts in a row on 2026-10-18 (`39111065875`). Commits `eb5a7841` and `a1839c01` are `git cherry-pick -x` of PR #6676 `8fb4595a` and `e93f4400` (head `e93f4400`, author Gracjan Kubicki), with `openai_responses_websocket_interrupt_window_test.go`. `12867514` is a downstream adaptation with the same behavior: it closes the window once, after the terminal branch, instead of inside it, so the completion branch where `patch/responses-ws-sse-incremental` adds its `onCompleted` hook stays untouched and the squash merge does not conflict. PR commit `2549efac` (waits for HTTP upstream cancellation in `TestResponsesInterruptStopsHTTPUpstream`) is not carried, because patch 10 already deflakes that test; on this branch alone, as on pristine `upstream/main`, the `./sdk/api/handlers/openai` package run fails that test often, with or without `-race` (`openai_responses_interrupt_test.go:376: http upstream was not canceled`; 4 of 5 runs on Windows and 3 of 5 in WSL without `-race` on 2026-10-18, 0 of 5 with patch 10). Verified 2026-10-18 under WSL `CGO_ENABLED=1 go test -race -count=60 -cpu 1,2` on the branch and on the full integrated candidate: 0 failures of the late-interrupt and window tests (3 of 60 before), and the whole `./sdk/api/handlers/openai` package passes under `-race`.
    - **Related Upstream Work**: PR [#6676](https://github.com/router-for-me/CLIProxyAPI/pull/6676) (carried). PR [#6621](https://github.com/router-for-me/CLIProxyAPI/pull/6621) makes the same fix without the `response.failed` case and currently conflicts. PR [#6515](https://github.com/router-for-me/CLIProxyAPI/pull/6515) is a broader rework that binds HTTP fallback interrupts to response IDs. Issue [#6483](https://github.com/router-for-me/CLIProxyAPI/issues/6483) (closed) reported the late-interrupt 400 that upstream `d318bcc3` addressed and whose test exposed this race.
    - **Retire when**: Upstream merges #6676, #6621, #6515 or an equivalent that closes the window at the terminal event. Check whether the adaptation commit is still needed on top of the merged form.

38. **`patch/thinking-validate-once`**
    - **Goal**: Stop validating the same Responses body several times while reading its reasoning effort.
    - **Scope**: `extractCodexUsageConfig` (`internal/thinking/apply.go`) validated the body and then called `extractConfigurationUpdateConfig`, which validated it again; it now calls `configurationUpdateConfig(body, true)` (`internal/thinking/configuration_update.go`). For a Responses body without a `configuration_update`, `ExtractReasoningEffort` validated it up to five times and walked `input` three times; Responses providers now go through `responsesReasoningEffort`, which validates once. `ExtractTranslatedReasoningEffort` no longer repeats the Responses read for `openai-response`.     - **Related Upstream Work**: None found (searched `ValidBytes`, `gjson.Valid`, validate once, repeated validation on 2026-10-18). Issue [#6711](https://github.com/router-for-me/CLIProxyAPI/issues/6711) (closed as not planned) asked to reject malformed bodies at the handlers, which would let the readers skip validation; upstream declined, so this patch keeps every reader's malformed-body behavior. ## Measured and Rejected

- **Tighter title-helper pre-filter** (2026-10-16). `isClaudeTitleHelperRequest` was 5.7% of the 2026-10-16 profile because upstream's `jsonMayContainASCII` (Issue [#6291](https://github.com/router-for-me/CLIProxyAPI/issues/6291), commit `5dbce4f3`) passes almost every Claude Code request: ordinary turns carry `output_config` (effort) and Go-escaped `\u003c`/`\u0026`. A needle-aware escape check that rejected those turns was exact (fuzzed against the reference walk) but slower: proving a needle absent needs a full scan of the body, which costs as much as the gjson walk it skips (3 MB Codex-to-Claude body: 2.2 ms → 2.8 ms per call). Indexing the top-level members once would save only one skim per call. The remaining lever is issue #6291's second suggestion, classifying the request once per `ExecuteStream`, which touches many executor call sites.
- **Faster JSON validator on the Responses WebSocket path** (2026-10-16). `encoding/json.Valid` was 0.44 s of the 4.54 s WebSocket-to-Codex path in the 21:09 profile: `normalizeResponsesWebsocketPassthroughRequest` (the only JSON gate for an incoming request; invalid JSON answers 400) and `websocketJSONPayloadsFromChunk` (drops invalid upstream lines, O(chunk), not O(request) like Issue #6665). Neither check is redundant, so the only lever is a faster validator. `gjson.ValidBytes` (v1.18.0, Go 1.27) is 5% faster on a 1 MiB Codex request (488 → 463 µs) and a 64 KiB `response.completed` event (32.6 → 30.9 µs), 25% on a 174-byte delta (123 → 92 ns), both allocation-free; that saves about 0.03 s per 15 minutes of this traffic. It also diverges on deep nesting: `encoding/json` rejects 20000 nested arrays, gjson accepts them through unbounded recursion, which weakens the gate on client input. Not worth it.

## Downstream Policy

- **No upstream pull requests.** This fork never opens pull requests against the upstream repository; the `Related Upstream Work` entries record upstream context only. Patches are maintained downstream indefinitely and are retired only when upstream lands an equivalent implementation, detected by a rebuild that finds the patch empty or conflicting.
- **`main` is intentionally unprotected.** The scheduled sync rebuilds and force-pushes `main`, so it carries no branch protection. Safety comes from `--force-with-lease`, the `upstream-sync-main` concurrency group, fail-closed conflict and empty-patch handling, and validation before the push. Protect the `patch/*` and `ci` branches against deletion instead; `main` is a derived artifact that nothing else may be based on.
- **Cross-repo patches.** Core and panel patches that depend on each other are listed under `Cross-repo` on both sides. Ship the provider side first.
